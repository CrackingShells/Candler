## Step 1: Probe P4, where an evaluator's strays appear
**Goal**: Know whether an evaluator's descendants are reparented to the job's supervisor, and whether they appear per request or only at the end, before the sweep's place in the body is fixed.
**Implementation Logic**:
1. In a throwaway test outside the committed tree (a scratch crate or an uncommitted test file, deleted afterwards), under LINUXRUN's image: call `become_subreaper()`, write a plug-in directory in a temp dir from the `engine_fixture` template whose kind starts `sh -c 'trap "" TERM; sleep 120'` through `python subprocess.Popen(..., start_new_session=True)` and returns `pass`, build its environment as `guard_engine`'s `rig` does, and run `evaluate` over two runs with `concurrency` 2.
2. While it runs, every 50 ms list the processes whose parent is the test's pid (from `/proc/<pid>/stat`, field 4) with their marker. Record: whether a stray has the test as parent after its evaluator exits; the time between the evaluator's exit and that; whether a stray ever has the test as parent while its evaluator is alive (it should not); whether the evaluator process itself, once exited, is a zombie child until `ZombieTick`-style reaping.
3. Answer in the leaf report, under `## P4`: "strays are reparented at the end of each request" or what was seen. The rule that follows: the body sweeps once, after the engine returns (needed by E3). It also sweeps after each run plan only if the strays outlive their request and the report shows they hold CPU or a slot-sized resource while later requests run.
4. Delete the throwaway. Nothing but the report is committed. Kill nothing: the strays are ended by the sweep under test, and what is left is the `sleep 120` that ends by itself; check with `pgrep` by marker that none is left, and leave any that is, naming it in the report.
**Deliverables**: `__reports__/m3-lean-cli/leaves/evaluate_body_v0.md`: its `## P4` section
**Consistency Checks**: `grep -q '^## P4' __reports__/m3-lean-cli/leaves/evaluate_body_v0.md && git diff --quiet <base> -- crates` (expected: PASS)

## Step 2: The evaluator pool and plug-ins from `plugins.dirs`
**Goal**: `slots.evaluators` is a user-config key and a setting with a default derived from the CPU count, `jobs/slots.rs` names the pool's directory, and `Registry` finds manifests in the directories `plugins.dirs` lists.
**Implementation Logic**:
1. Write the guards first and see them red. Each doc carries `Guards:`, `Oracle:` and `Bite:`.
   - `e2_user_config_reads_slots_evaluators_and_refuses_a_bad_value` (`guard_resolve.rs`): absent → `None`; `3` → `Some(3)`; `-1`, `"x"` → `ConfigError::WrongType` naming `slots.evaluators`; a project `candler.toml` with `[slots] evaluators = 2` → `MachineWideKey` naming it. Bite: the key accepted in a project file.
   - `e2_slots_evaluators_is_a_setting_not_a_cell_value` (`guard_resolve.rs`): `is_setting("slots.evaluators")` is true, `slots.evaluator` is false, and a user config value shows in a resolution's `settings` with the source `user_config`. ## Step 3: The engine takes slots, selects, and reports each outcome
**Goal**: A request waits for an evaluator slot instead of a tokio permit, a request carries a marker of its own, the engine selects runs by `RunSelection`, writes its child records where the caller says, and emits one `evaluation.outcome` per record it commits.
**Implementation Logic**:
1. Add a plug-in fixture to the engine fixtures first: `kinds/engine_pool.py` (the plug-in `pool`: an `interval` kind that appends `<pid> start <monotonic>` to the file its `file` param names, sleeps `sleep_s` seconds (an optional param, default 0.5; `evaluate_verb`'s Ctrl-C guard sets it high), appends `<pid> end <monotonic>`; a `stray` kind that starts a `start_new_session` child running `sh -c 'trap "" TERM; sleep 300'`, writes its pid to the file its `pidfile` param names and returns pass; an `ok` kind), `plugin_pool.toml`, `suite_pool_ok.toml` (one `ok` entry), `suite_pool_interval.toml`, `suite_pool_stray.toml`, and the README rows. `evaluate_verb` reuses these files. Then write the guards in `guard_engine.rs` and see them red:
   - `e2_one_evaluator_slot_serialises_requests_and_two_overlap`: two runs, `EvaluatorSlots` count 1 then 2. The interval lines of the plug-in must not overlap with 1 and must overlap with 2 (the positive control). While it runs, the test polls `Slots::held()` of the pool directory: a holder whose `job` is the test's job string is seen. Bite: the tokio semaphore kept.
   - `e2_agent_slots_held_by_a_job_do_not_delay_an_evaluator`: every slot of the agent pool directory is held through `Slots::acquire`; the evaluation, with its own pool of 1, ends inside 60 s with no failed request. Bite: evaluators drawing from the agent pool.
   - `e1_engine_emits_one_outcome_event_per_committed_record`: through `evaluate_reporting` with a recording sink: the `evaluation.outcome` events number the records of `report.outcome_files` read back from the store, each carries its run key, and each record equals its file's line; a cancelled call (the cancel sent before the batch starts) emits none and commits no file; a failed request emits none. Bite: records committed with no event; an event sent before the commit.
   - `e1_selection_keys_and_pending_pick_the_runs_they_name`: `Keys` grades exactly the keys it holds. After a call with `Glob` over one run, `Pending` grades the other runs and not that one, and a second `Pending` grades none. Bite: `Pending` selecting every run; `Pending` treating an outcome file of another evaluator version as complete.
   - `e3_each_request_carries_its_own_marker`: after a two-run call with `record_dir` set, the markers of the child records in it are distinct, each starts `evaluation-`, and none is `candler-evaluation`. Bite: the constant marker back. Why: `ProcMarkerSweeper` kills by an exact marker, and the sweeper this leaf installs would end another job's evaluators that share it.

## Step 4: The evaluate job body
**Goal**: `JobSpecFile::Evaluate(EvaluateSpec)` and `jobs/runtime/evaluate.rs` run an evaluation under the job protocol with a subreaper, a sweep and the job's own records, and E1 and E3 hold for the job.
**Implementation Logic**:
1. Write the guards first in `tests/guard_evaluate_job.rs`, with `tests/support/job_evaluate.rs` holding the re-exec entry as `guard_job_runtime`'s `supervisor_child` does (the test binary run again, with the job, the store and the work directory in `CANDLER_TEST_*` variables, running `supervise_evaluate`), and see them red:
   - `e1_a_run_spec_keeps_its_bytes_in_the_spec_file`: `JobSpecFile::Run(job_spec())` serialises to the same bytes as `job_spec()` alone, and an `Evaluate` spec round-trips and does not read as a `Run`. If the scaffold's encoding of `Run` is not the bare object, report it and keep the other row. Bite: a `Run` spec whose bytes moved.
   - `e1_the_evaluate_job_ends_with_one_outcome_event_per_committed_record`: a job over the `pool` plug-in's `ok` suite and two runs. Its `events.jsonl` holds `job.started` first, then one `evaluation.planned` whose `outcomes` is the number of records the job tries (P6, added by `contract_wire`), one `evaluation.outcome` per record of the store's outcome files, and `job.ended(completed)` last; `report.json` in the job directory equals `to_document()`. Bite: outcomes committed with no event; no `evaluation.planned`, or one emitted after the first outcome.
   - `e1_the_evaluate_job_refuses_a_changed_suite_and_zero_slots`: a suite file edited after the spec was written ends the job `failed` before any process starts; `slots.evaluators = 0` in the user config ends it `failed` with "no evaluator slot", not a hang. Bite: the digest unchecked; the zero read as the default.
   - `e3_a_setsid_term_ignoring_stray_of_an_evaluator_is_dead_by_job_ended` (Linux): the `stray` suite; at `job.ended` the pid the kind wrote is gone with its recorded start time (`kill(pid, 0)` and `process_start`, as `b33` reads them). Bite: no subreaper, or no sweep.
   - `e3_a_lost_evaluate_job_is_recovered_and_its_evaluator_is_reaped` (Linux): the child supervisor, killed through the `std::process::Child` the test started while an `interval` request is in flight, leaves the lock free and no `job.ended`; `recover_job_dir` ends the evaluator process from the job's `children/` record, and `classify` reads `Ended`. Bite: the engine's records outside `children/`. The stray of a lost job is not asserted: the recovery has no marker sweeper, as for a run job.
