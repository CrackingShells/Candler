## Step 2: One `/proc` parser, and a parent that two sources agree on
**Goal**: `/proc/<pid>/stat` is parsed in one place that returns the process id, state, parent, group and start ticks, and the parent and group are accepted only when `/proc/<pid>/status` says the same, with up to 3 re-reads for a process reparented between the two reads.
**Implementation Logic**:
1. Write the S4 guards first in the new `tests/guard_proc_stat.rs` and see them fail to compile or fail. The file spawns a process in one row, so it is a binary of its own: `guard_signal` promises never to spawn. Every guard doc carries `Guards:`, `Oracle:` and `Bite:`.
   - `s4_proc_stat_reads_every_field_for_any_command_name`: literal lines whose command is `sleep`, `a) S 1 1 (b`, one holding spaces, `((`, `))`, a 15-byte name, an empty name `()` and one holding a newline. Each row's pid, state, parent, group and start ticks were chosen before the line was built.
   - `s4_proc_stat_refuses_a_line_that_is_not_a_stat_line`: no `(`, no `)`, a close before the open, no pid, a non-numeric parent, fewer than 22 fields.
   - `s4_proc_status_reads_ppid_and_the_leftmost_nspgid_by_key`: `key:\tvalue` lines; `NSpgid:` with two values takes the first; a status with no `NSpgid:` gives `None` for the group only; a `Name:` value that contains `PPid:` is not the key.
   - `s4_cross_check_refuses_when_stat_and_status_disagree_on_every_read`: a reader seam whose `stat` says parent 5 and `status` says `PPid: 6` on every read. The answer is `None` and the reader was asked exactly `CROSS_CHECK_READS` pairs, no more.
   - `s4_cross_check_accepts_a_disagreement_that_clears_on_a_reread`: the first pair disagrees (a reparent between the two reads), the second agrees. The answer is the second pair's parent, after two pairs.
   - `s4_a_real_process_with_a_hostile_name_reads_back_its_true_parent` (`#[cfg(target_os = "linux")]`): a symlink named `x) S 1 1 (y` in a temp dir to `/bin/sleep`, started with `CommandExt::arg0("sleep")` and `1` as argument, so the kernel writes the line. Read it through `read_proc_stat`: its parent is this test's pid and its group is `getpgrp()`. The child ends by itself after a second and is waited for; no signal is sent.
2. `src/supervise/platform.rs`: add `pub struct ProcStat { pub pid: u32, pub state: char, pub parent: u32, pub group: u32, pub start_ticks: u64 }` with `ProcStat::parse(line: &str) -> Result<Self, SuperviseError>`. It keeps `parse_proc_stat`'s method exactly (pid before the first `(`, fields resume after the last `)`; field 22 is the 20th after it) and adds fields 3 to 5. `pub fn parse_proc_stat(line) -> Result<u64, SuperviseError>` stays, as `ProcStat::parse(line).map(|stat| stat.start_ticks)`, so `public_surface.rs` and `read_start` do not change. Why one parser: today the start and the parent come from two functions over the same line, and the parent one has no test.
3. Same file: `pub struct ProcStatus { pub pid: u32, pub parent: u32, pub group: Option<u32> }` and `ProcStatus::parse(text: &str) -> Option<Self>`: line by line, a key is the text before the first `:` of a line and must equal `Pid`, `PPid` or `NSpgid` exactly; the `NSpgid` value is its leftmost number (the id in the namespace procfs was mounted in, proc(5)). Why: a command name cannot shift a `key:\tvalue` line, so it is independent of the `stat` parse. A kernel older than 4.1 has no `NSpgid:`; the group is then checked from `stat` alone.
4. Same file: `pub enum ProcFile { Stat, Status }`, `pub const CROSS_CHECK_READS: u32 = 3`, `pub fn read_proc_checked(pid: u32, read: &dyn Fn(u32, ProcFile) -> Option<String>) -> Option<ProcStat>` and `pub fn read_proc_stat(pid: u32) -> Option<ProcStat>` (the real `/proc` reader, Linux only; `None` elsewhere). `read_proc_checked` reads a `stat` and a `status`, requires both pids to equal `pid`, and accepts only when `parent` agrees and, where `status` has one, `group` agrees. On disagreement it reads the pair again, up to `CROSS_CHECK_READS` pairs; it refuses (`None`) when the last pair still disagrees. Why the loop: an orphan reparented between the two reads gives a false disagreement, which would leave it alive, which is the defect being fixed. The seam is a parameter, not the `Guard` inspector: the inspector replaces `read_facts` as a whole, after this check.
5. `src/supervise/signal.rs`: delete `state_parent_group`; `read_facts` takes state, parent and group from `read_proc_stat(pid)`. Everything else in `read_facts` (the start read before and after, the uid, the marker) is unchanged.
6. Run the guards green. Run SPAWN's first half on the committed tree before the Linux runs.
**Deliverables**: `crates/candler-core/src/supervise/platform.rs`: `ProcStat`, `ProcStat::parse`, `ProcStatus`, `ProcStatus::parse`, `ProcFile`, `CROSS_CHECK_READS`, `read_proc_checked`, `read_proc_stat`, `parse_proc_stat` (now a wrapper); `crates/candler-core/src/supervise/signal.rs`: `read_facts` without `state_parent_group`; `crates/candler-core/tests/guard_proc_stat.rs`: the six `s4_` guards above
**Consistency Checks**: `! git grep -n 'fn state_parent_group' -- crates && cargo nextest run -p candler-core --no-tests=fail -E 'test(/^s4_/) | binary(public_surface)'` (expected: PASS)
**Commit**: `fix(jobs): read a process's parent from two sources that agree`

## Step 3: An orphan in the supervisor's tick is signalled
**Goal**: `adopted()` orders starts with `>=` on Linux ticks of one boot and on darwin `(sec, usec)`, still refuses an earlier start, another boot, another kind and `unavailable`, and S1 and S2 pin it.
**Implementation Logic**:
1. Amend S1 and S2 first and see them red against the strict code.
   - `signal_adopted_orders_linux_starts_by_boot_and_ticks` (keeps its name): the rows are fewer ticks → refused, the same ticks → signalled, another boot → refused, more ticks → signalled; the fake's single-signal log now holds the two signalled pids. Its `Bite:` line reads: restore `>` in the Linux arm (the same-ticks row goes red); loosen the comparison to `true` (the fewer-ticks row goes red).
   - `signal_adopted_refuses_all_but_a_verified_orphan_and_its_verified_group` (keeps its name): the darwin row labelled "started before the caller", whose start equals the caller's (100), is really a same-start row. Relabel the rows: start 99 → refused ("started before the caller"), start 50 → refused ("by a later clock"), and add start 100 → signalled ("the caller's own start"). The refused-rows table keeps 8 rows. Its `Bite:` adds: leave the darwin arm strict.
   - Both expect the new reason text `the process started before the caller`.
2. `src/supervise/signal.rs`: rename `started_after` to `started_no_earlier` and make it `>=` in both arms; the arms that never order (different boots, different kinds, `unavailable`, a missing number) stay `false`. In `adopted()` and in the doc of `signal_adopted`, "started after the caller" becomes "started no earlier than the caller", and the refusal detail is `the process started before the caller`. Why `>=`: the kernel counts a Linux start in 10 ms ticks, so a descendant spawned within 10 ms of the supervisor has the supervisor's own tick, and the parent check already proves it is a descendant (R10 §1, the table "Why `>=` stays safe").
3. Do not touch `signal_group`, `signal_marked`, `register`, the leader re-check, the start equality check or the container guard.
