## Step 1: First reads and the four guards, seen red
**Goal**: The leaf knows where N4's rule and N6's check live, and each guard fails on the tip.
**Implementation Logic**:
1. Through colgrep (index `crates/candler-core`, `crates/candler-harness` and `crates/candler-harness-claude-code` of this worktree, one at a time): `PlanOutcome` and `PlanMode::Check` in `runner/plan.rs`; `TreatmentIdentityStep` in `resolve/steps/identity.rs` and `SkillTree` in `candler-harness/src/skills.rs`; the reader of `replicates` (`plan.rs` `run_order`) and `check_set_paths` and `request_settings` in `commands/preflight.rs`; the rule that demands a `[treatment]` default when `request.treatment` is the factor; the run-time check that refuses a prompt starting with `/`. Verify each of R16's claims for these ids; a false one goes to the coordinator.
2. Guards, each with a `Guards:` line and an oracle written in the test:
   - `skill_tree_missing_at_the_commit_is_refused` (G5, I7): one added tag in the existing git fixture of `b22_skill_tree_is_the_tag`, whose commit lacks the skill subtree; `resolve` refuses it and names the path;
   - `set_replicates_is_honoured` (N2): a file with `replicates = 5` and `--set replicates=1` plans one run per cell, and the resolution records the value's source as explicit;
   - `treatment_factor_needs_no_default` (N4): an experiment whose `request.treatment` factor levels each give a source and a tag, with no `[treatment]` table, resolves; an experiment with neither is still refused;
   - `slash_prompt_is_refused_at_resolve` (N6): a prompt starting with `/` is refused by `resolve` with the code it gets at run time today.
3. If the first read shows that `replicates` enters the cell identity, N2 becomes "refuse `--set replicates` at resolve, naming it a file field": change that guard to expect the refusal and report it.

## Step 2: The plan summary and the skill tree check
**Goal**: `PlanOutcome` has a summary for `resolve` to print; G5's guard passes.
**Implementation Logic**:
1. `PlanOutcome::summary()` returns cells, new runs (`plans.len()`), reused runs (`sealed.len()`) and the cap bounds (run count times the per-run `wall_s`, and the job caps), all already computed by a Check-mode plan; no new planning pass, no store write. The experiment stays an experiment (R01: never called a plan).
2. The treatment step asks `SkillTree` whether the tree exists at the pinned commit and fails the step with the path named, as a preflight check id of the form `<step>.<check>`; no `codes.toml` row.
**Deliverables**: `crates/candler-core/src/runner/plan.rs`: `PlanOutcome::summary`, `PlanSummary`; `crates/candler-core/src/resolve/steps/identity.rs`: the skill-tree check; `crates/candler-harness/src/skills.rs`: the lookup at a commit
**Consistency Checks**: `cargo nextest run -p candler-harness-claude-code --no-tests=fail -E 'test(/^guard_claude_code_driver::/)' && cargo nextest run -p candler-core --no-tests=fail -E 'test(/^guard_run_plan::/) | test(/^guard_resolve::/)'` (expected: PASS)
**Commit**: `feat(resolve): refuse a pinned commit that lacks the skill tree`

**Implementation Logic**:
